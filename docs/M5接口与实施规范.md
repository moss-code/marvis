## 2. IPC 契约增量（src/shared/ipc.ts）

| channel | 方向 | 签名 | 说明 |
|---|---|---|---|
| `chat:cancel` | invoke | `(runId: string) => void` | 取消当前 run；runId 不匹配或无运行中任务时静默返回（不抛错） |
| `chat:clear` | invoke | `() => void` | 清空 chat_messages 表；不动 reports / runs / data_ 表；运行中抛错 |
| `run:list` | invoke | `() => RunMeta[]` | 倒序，≤50 条 |
| `run:get` | invoke | `(runId: string) => AgentEvent[] \| null` | 完整事件序列，供回放与日志查看 |
| `db:dropTable` | invoke | `(table: string) => TableSchema[]` | 删除一张 data_ 表，返回最新表列表；校验见 6.2 |
| `report:delete` | invoke | `(reportId: string) => ReportMeta[]` | 删除报告，返回最新列表 |
| `config:get` | invoke | `() => ModelConfig` | apiKey 类字段脱敏 |
| `config:save` | invoke | `(c: ModelConfig) => void` | 写回 `.env` 并即时生效（见第 4 节）；运行中抛错 |

`WindowApi` 新增：`chatCancel / chatClear / listRuns / getRun / dropTable / deleteReport / getConfig / saveConfig`。preload 的 `index.ts` + `index.d.ts` 同步（老规矩，三处同步）。

## 3. 任务取消规范（P0，最高优先）

### 3.1 主进程（src/main/agents/index.ts + ipc.ts）

1. `ipc.ts` 持有 `currentRun: { runId: string; controller: AbortController } | null`；`chat:send` 受理时创建，`startRun` 的 finally 中置 null。
2. `chat:cancel` handler：runId 匹配时 `controller.abort()`，**只 abort 不清 running 标志**（由 startRun 的 finally 统一清，避免竞态）。
3. `startRun` 接收 `signal: AbortSignal`，贯穿传递：
   - 领队马 `streamText({ ..., abortSignal: signal })`
   - 子马 `generateText({ ..., abortSignal: signal })`（signal 经 TaskCtx 透传）
   - MCP/内置工具：AI SDK 会把 abortSignal 注入 tool execute 的 `options`，现有 `wrapTool` 已透传 options，无需改动
4. **AbortError 的收尾路径**（关键）：
   - 子马执行器 catch 到 abort（`err.name === 'AbortError'` 或 message 含 abort）：发 `task_failed(reason='用户取消了本轮任务', retriesUsed=0)` 保证 taskId 终态闭合，返回 `任务已被用户取消`。
   - `startRun` 的外层 catch 识别 abort：落库领队马消息「本轮任务已被您取消」，发 `run_finished(ok=false, finalText='本轮任务已被您取消')`。
   - **run_finished 必须有且只有一次**：正常分支与 catch 分支共用一个 `finished` 布尔守卫。
5. （P1）`runSkillScript` 接收 signal，abort 时 `child.kill('SIGTERM')`。

### 3.2 渲染进程

- ChatDock：running 时输入条右侧显示「■ 停止」按钮（error 色调描边），点击 `chatCancel(当前 runId)` 后按钮变「停止中…」并禁用；store 需保存当前 runId。
- 解锁与场景复位完全依赖 `run_finished` 事件（现有机制），渲染进程不做本地强制解锁。
- 取消属于正常操作：**不播 task_failed 的道歉摇头动画的加长版**——沿用现有演出即可，无需特判。

## 5. 任务历史与场景回放规范（P0）

> 定位声明：回放是**对真实历史任务的透明重演**，UI 全程显著标注「回放」，与 PRD「不做隐藏假结果」不冲突；培训讲解多 Agent 协作机制时可反复重放。

### 5.1 主进程：runs 表增强（src/main/db/index.ts）

现有 `runs(id, events_json, created_at)` 缺摘要列，`run:list` 不得全量解析 events_json。幂等迁移：

```sql
ALTER TABLE runs ADD COLUMN user_query TEXT;     -- try-catch 包裹，列已存在则忽略
ALTER TABLE runs ADD COLUMN ok INTEGER;
ALTER TABLE runs ADD COLUMN duration_ms INTEGER;
ALTER TABLE runs ADD COLUMN event_count INTEGER;
```

- `saveRun` 改为同时写入四个摘要列（从事件数组的首尾事件派生：`run_started.userQuery`、`run_finished.ok`、时间差、长度）。
- 老数据（摘要列为 NULL）：`run:list` 时跳过或显示「（早期记录）」，不做回填。
- `run:get`：解析 events_json 返回 `AgentEvent[]`；JSON 损坏返回 null。

### 5.2 渲染进程：历史面板与回放导演

**入口**：标题栏新增「任务历史」按钮 → modal 面板（沿用既有 panel 视觉）：

- 列表行：时间 / userQuery（截断）/ 成败徽标 / 耗时 / 「查看日志」「回放」两个操作。
- 「查看日志」：以 TaskLog 的条目样式静态渲染该 run 的事件序列（只读，不影响右侧实时日志）。
- 「回放」：进入回放模式。

**回放模式（ReplayDirector，src/renderer/src/replay/）**：

1. 与真实任务互斥：`store.running === true` 时回放按钮禁用；回放中 `store.replaying = true`，ChatDock 锁定并提示「正在回放历史任务」。
2. **事件隔离（最关键）**：回放事件**只送** SceneDirector、AudioDirector 与一个独立的回放日志视图；**绝不调用 `store.handleEvent`**（否则污染对话记录、报告列表与持久层）。TaskLog 顶部出现可关闭的「回放中」横幅，正文临时切换为回放事件流，结束后恢复。
3. 节奏：事件本身无时间戳，用固定间隔重演——`leader_say` 逐条 30ms、`tool_call_started → finished` 之间 1200ms、其余事件间 800ms；提供 1x / 2x 倍速切换；「停止回放」立即清空待播队列并发一条合成的 `run_finished` 给 SceneDirector 复位场景。
4. 回放遇到 `report_ready`：白板照常播贴纸动画，但**点击打开的是真实存量报告**（reportId 仍有效；报告已被删除时气泡提示「该报告已删除」即可）。
5. 屏幕右上角常驻半透明「回放 ▶」徽标，结束自动消失。

## 6. 数据管理规范（P0）

### 6.1 UI（SettingsPanel 新增「数据」tab）

- **数据表区**：每表一行（表名 / 行数 / 列数），「预览」展开抽样 5 行（复用 TableSchema.sampleRows），「删除」弹确认（原生 dialog 或应用内确认均可，文案含表名与行数）。
- **对话区**：「清空对话」按钮 + 确认；成功后 store.chat 置空。
- **报告区**：报告列表（标题/时间），「删除」带确认；删除后若 ReportPanel 正开着该报告则关闭。

### 6.2 主进程校验（防注入，必须全部满足）

`db:dropTable`：

1. `table` 必须以 `data_` 开头；
2. 必须存在于 `sqlite_master`（`type='table'` 精确匹配查询结果，**用查到的名字拼 SQL**，不用入参原文）；
3. 拼接时双引号转义（沿用 `recreateDataTable` 的 `replaceAll('"','""')` 模式）。

三个删除类 handler 在 `running === true` 时一律抛「小马们正在干活」。

### 6.3 联动

- 删表后：`db:listTables` 结果即新状态；下一轮 run 的 prompt 自然不再含该表（schema 每轮实时读取，无需额外处理，验收时确认）。
- 删报告后：白板「点击打开最新报告」逻辑指向新的最新一份；全删后白板贴纸移除（OfficeScene 暴露 `clearPin()` 或复用 pinReport 重绘）。
- 清空对话后：领队马 `messages` 历史自然变空（实时读库），重启不恢复旧对话。

## 9. 已知坑位（务必避开）

1. **回放污染（本阶段最大坑）**：回放事件如果走 `store.handleEvent`，会把历史 userQuery 追加成新聊天记录、把 report_ready 重复插入报告列表。回放必须走独立通道，验收标准里专门设了「零污染」检查项。
2. **run_finished 双发**：abort 时 `streamText` 的 fullStream 可能先抛错进 catch，而子马 dispatch 的 finally 也在收尾——用单一 `finished` 守卫确保 run_finished 只发一次；`saveRun` 永远在 finally。
3. **AbortError 识别**：AI SDK 各层包装后错误形态不一（`AbortError` / `ResponseAborted` / message 含 "abort"），统一写一个 `isAbortError(err)` 工具函数判断，宁可宽松（误判为取消也只是文案差别）。
4. **取消与 MCP 确认框**：abort 不会自动关闭正在显示的原生确认框，用户需手动点掉；在 `confirmDestructive` 之前检查 `signal.aborted` 可减少窗口期，文档化为已知行为即可，不必强求完美。
5. **.env 写回丢内容**：禁止「读成对象再序列化」的重写方式（会丢注释和未知键）；必须逐行处理。写文件用临时文件 + rename 防止写一半断电损坏。
6. **node:sqlite 的 ALTER TABLE**：`ADD COLUMN` 重复执行会抛错，每条 ALTER 单独 try-catch（错误信息含 "duplicate column" 时忽略），保证 initDb 幂等。
7. **run:list 性能**：摘要列就是为了避免解析 events_json（单条可达数百 KB）；SELECT 时**不要**带 events_json 列。
8. **回放的 SceneDirector 队列**：回放停止时场景可能还有排队中的行走动画，必须像真实 `run_finished` 一样走既有复位路径（合成事件喂给 SceneDirector），不要直接操作 actor。
9. **渲染进程永不持明文 key**：config:get 脱敏在主进程完成；前端表单状态也只存脱敏值或用户新输入。
10. **拖拽文件路径**：Electron 新版本中 `File.path` 已废弃，必须经 preload 用 `webUtils.getPathForFile` 转换；直接在渲染进程拿 path 会得到 undefined。
11. **协议冻结（再次强调）**：取消复用 `task_failed` + `run_finished(ok=false)`，回放复用全部既有事件，不得新增 AgentEvent 类型。
